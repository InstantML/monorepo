# Design: Landing, Auth, And Onboarding

Date: 2026-05-11

Status: Implemented first slice

Owner: Codex

## Summary

Training Observability needs a hosted entry flow before the dashboard. First-time users should land on a product page, continue through a Google-style sign-in or sign-up screen, choose an individual or business account path, create or join an organization, create an SDK API key, and then reach the existing dashboard.

The smallest useful version keeps the current local-first developer experience while adding the core hosted model: user UUIDs mapped from verified emails, org memberships, opaque browser sessions stored as hashed tokens, org seat limits, and copy-once API key creation. Real Google token verification stays behind the existing managed-auth boundary and configuration; local development uses an explicitly labeled dev Google flow that exercises the same user/org/session/API-key paths without requiring OAuth credentials in the repo.

This design also replaces hash-tab navigation with real Next routes so dashboard state is shareable and auth redirects are predictable.

## Goals

- Show unauthenticated visitors a polished landing page before app access.
- Support Google-style sign in and sign up for individual customers and business organizations.
- Map email identities to stable user UUIDs and authorize tenant data through user UUID plus org membership.
- Let org owners/admins create and copy an SDK API key during onboarding.
- Add organization seat management primitives without building a full invitation email system yet.
- Move dashboard navigation from `/#tab` to `/dashboard/:tab` routes while preserving current dashboard behavior.
- Keep local Rust development and existing SDK/API-key compatibility working.

## Non-Goals

- Full production Google OAuth redirect/callback UI with third-party credentials committed in the repo.
- Password auth, magic links, billing checkout, SCIM, SAML, or email delivery.
- Fine-grained dashboard role permissions beyond owner/admin/member/viewer checks needed for onboarding and API-key creation.
- Removing deprecated Node compatibility smokes.
- Persisting all dashboard local-storage views to Postgres.

## Users and Use Cases

Visitors evaluate the product, understand that it is a fast training observability tool for LLM/RL workloads, and choose to sign in.

Individual customers create a personal org, create an API key, and reach the dashboard quickly.

Business users create a team org, optionally reserve seats for teammate emails, create an API key, and then land in the dashboard.

Existing local developers can still run the Rust API and Next app without Google credentials, use the dev Google flow, and keep SDK ingestion working with local or API-key auth.

## Proposed Design

### Route Flow

- `/`: landing page for unauthenticated visitors. It explains the product, speed posture, supported workflows, and SDK-to-dashboard loop. Authenticated users can continue to `/dashboard/runs`.
- `/signin`: compact Google-style sign-in screen. In local/dev mode it accepts name and email and posts to the dev auth endpoint. In hosted mode it is the shell for managed Google sign-in.
- `/signup`: account selection and Google-style sign-up. The user chooses `customer` or `business`, enters email/name, and for business enters an org name.
- `/onboarding`: authenticated setup checklist for org name, account type, optional seat emails, API-key creation, and final dashboard entry.
- `/dashboard`: redirects or normalizes to `/dashboard/runs`.
- `/dashboard/:tab`: existing dashboard shell with `runs`, `metrics`, `detail`, `compare`, `alerts`, `datasets`, `artifacts`, `models`, `reports`, `settings`, `integrations`, and `api`.
- `/#tab`: no longer generated by the UI. If a user opens an old hash URL, client code normalizes the hash to the matching `/dashboard/:tab` path.

A shared route helper owns `tabToPath`, `tabFromPath`, legacy-hash normalization, and `next` sanitization. `next` must be a same-origin relative path beginning with `/dashboard`, `/onboarding`, or `/`; absolute URLs, protocol-relative URLs, and paths containing control characters are rejected and replaced with `/dashboard/runs`.

Route-backed dashboard navigation must use real route semantics, not button-only pseudo-navigation:

- Left-rail items render as links or link-equivalent controls with `aria-current="page"` for the active tab.
- Tab changes use replace-style navigation so ordinary tab switching does not flood browser history.
- Unknown `/dashboard/:slug` paths normalize to `/dashboard/runs`.
- Legacy hashes normalize once with `history.replaceState`.
- Focus moves to the active page heading or status region after route changes.
- Existing lazy data boundaries stay tied to the active tab so direct-loading `/dashboard/metrics` does not fetch Run Detail, Compare, or artifact-only data early.
- The dashboard client shell should stay mounted across tab changes where practical. The implementation must test that Runs -> Metrics -> Runs preserves selected runs and does not issue extra initial summary/panel fetches beyond the expected active-tab requests.

### Visual Direction

The landing page should look like the dashboard grew an exterior wall, not like an unrelated SaaS template. Use the existing low-radius, dark/light token system, precise line work, restrained shadows, dense product signals, and real dashboard UI motifs. The first viewport should include the product name, concise value proposition, primary Google auth action, and a live-looking dashboard/metric preview built in HTML/CSS using actual metrics language.

The sign-in, sign-up, and onboarding screens should be compact operational surfaces. Use segmented controls for business/customer, icon buttons where familiar, clear progress affordances, copy-once API key display, and no decorative marketing blobs. Copy should emphasize speed, local-first SDK onboarding, and training-loop confidence.

Concrete first viewport composition:

- Product name as the H1: `Training Observability`.
- Supporting copy: implemented strengths only, such as fast run browsing, bounded metric charts, SDK ingestion, Rust/Postgres storage, and local-first setup.
- Primary action: Google sign-in only when managed auth is configured; otherwise the local dev flow is explicit and labeled.
- Secondary action: open the local demo/dashboard path after auth.
- Product preview: a compact dashboard shell with a run table, metric chart, compare row, and SDK/API-key snippet. This should be CSS/HTML product UI, not decorative illustration.
- Responsive acceptance: at `720px` and below the preview stacks under copy, code/API-key blocks wrap or horizontally scroll inside their own container, and no text is allowed to overlap buttons or metrics.
- Accessibility acceptance: visible `h1`, labeled inputs, error summary for failed forms, keyboard-only completion, `aria-live` copy/auth states, accessible provider-button names, and no required animation when `prefers-reduced-motion` is set.
- Auth/onboarding accessibility: main/H1 focus after redirects, `aria-busy` or `role="status"` during session checks, field-level errors with `aria-describedby`, native radio or radiogroup semantics for account type, keyboard-reachable seat editing, and polite live announcements for copy-once API key copy.

### Auth Model

Use existing identity tables as the source of truth:

- `users.primary_email` remains unique `citext`; this is the email to user UUID mapping.
- `user_identities(provider, provider_subject)` maps Google/dev identities to a user UUID.
- `memberships(org_id, user_id)` maps users to organizations with roles.
- Tenant-owned product data continues to be indexed by `org_id`, project/run IDs, and maintained summary tables, not email.

Add opaque browser sessions:

- The browser receives only a random session token in an `HttpOnly`, `SameSite=Lax` cookie.
- Postgres stores only `sha256(token)` plus user/org IDs and expiry.
- The session cookie is `Secure` when the request is not localhost.
- The server updates `last_seen_at` at most once per minute to avoid write amplification.
- Logout revokes the session row.

Session auth and API-key auth coexist:

- Browser dashboard/API-key/org routes use session auth.
- SDK ingestion continues to use bearer API keys.
- In `RLOBS_AUTH_MODE=local`, compatibility product routes can still use the fixed local org when no session is present. Session-authenticated requests use the session org instead.
- In `RLOBS_AUTH_MODE=api-key`, tenant product routes require either a valid API key or valid session, depending on route class. SDK write scopes still use API-key scopes.

### Local Dev Google Flow

Because the repo cannot ship Google OAuth credentials, add a local-only endpoint:

- `POST /api/auth/dev/google`
- Enabled only when `RLOBS_AUTH_MODE=local` and either the bind address is loopback or `RLOBS_DEV_AUTH_ENABLED=true` is set for an explicitly local development process. It must not run in hosted/API-key mode.
- Accepts `email`, `display_name`, `account_type`, `org_name`, and optional `seat_emails`.
- Validates email/name/account type, upserts user and dev identity, creates a new org or returns `409` on slug conflict, creates membership, stores a session, and returns current session payload.
- The UI labels this as a local development Google-style flow.

Add a production-shaped endpoint now but keep it explicit:

- `POST /api/auth/google`
- If managed Google verification is not configured, returns `501` or `401` with a client-safe error.
- When a verifier is configured later, it should validate the Google ID token, then call the same store onboarding function as the dev route.

Add provider availability discovery:

- `GET /api/auth/config`
- Returns whether local dev auth and managed Google auth are enabled.
- The frontend must not present a broken primary Google action. In production, hide or disable Google sign-in until configured. In local development, show the dev Google-style form clearly as a development shortcut.

### Onboarding And Seats

Organizations gain an `account_type` and `seat_limit`:

- `account_type`: `customer` or `business`.
- `seat_limit`: default `1` for customer orgs and `3` for business orgs.

Memberships gain a `status`:

- `active`: current signed-in user or accepted teammate.
- `invited`: reserved seat for a teammate email in the local first slice.

Seat reservation route:

- `POST /api/orgs/:org_id/seats`
- Session owner/admin only.
- Creates or reuses a user row by email, inserts membership with `status='invited'` and requested role, and rejects the request with `409` when active plus invited seats would exceed `seat_limit`.
- Enforces the seat limit inside one transaction that locks the organization row with `for update`, counts active plus invited memberships, and inserts the reserved membership before commit.
- This does not send email yet; it only creates durable mapping data and UI visibility.

The onboarding page lets business users reserve a few teammate emails, but the UI must say that no invitations are sent yet and show a visible seat counter. API key creation remains the main completion gate. Full invitation email delivery moves to a later admin/settings slice.

### API Key Creation

The existing API key store path is reused to keep API-key behavior and hashing consistent. Session owner/admin requests can call:

- `POST /api/orgs/:org_id/api-keys`
- `GET /api/orgs/:org_id/api-keys`

The handler should authorize through bootstrap, API key with `api_keys:write`, or session owner/admin. The plaintext API key is returned once and displayed in onboarding with copy affordance and SDK setup command. The UI should never store the plaintext key in local storage.

Local-mode product fallback and admin authorization must be separate. Unauthenticated local product reads/writes can continue to use the fixed local org for compatibility, but org admin routes such as API-key creation and seat reservation require one of:

- valid owner/admin browser session for the requested org,
- unrestricted org API key with `api_keys:write`,
- configured bootstrap token.

`RLOBS_AUTH_MODE=local` alone is not sufficient admin authorization.

### Dashboard Session Handling

Add:

- `GET /api/auth/session`: returns `{ authenticated, user, organization, memberships, account_type }`.
- `POST /api/auth/logout`: revokes cookie session and clears the cookie.

Dashboard pages check session on entry. Unauthenticated users reaching `/dashboard/*` are sent to `/signin?next=/dashboard/runs`. Local smoke tests can sign in through the dev endpoint before entering the dashboard.

Saved dashboard view keys should include org/user when a session is present, while preserving old local keys as read-only legacy fallback.

Cookie-auth mutating routes must check request origin and require a same-origin or configured allowed frontend origin. The implementation may add a double-submit CSRF token later, but this slice must at least reject cross-site state-changing browser requests before accepting session cookies.

## Data Model

`organizations` changes:

- `account_type text not null default 'customer' check in ('customer', 'business')`
- `seat_limit integer not null default 1 check (seat_limit > 0 and seat_limit <= 10000)`
- Index: existing slug/org indexes remain sufficient for onboarding.

`memberships` changes:

- `status text not null default 'active' check in ('active', 'invited')`
- Index: `(org_id, status, created_at desc)` for seat list and usage counts.
- Existing unique `(org_id, user_id)` remains the seat uniqueness guard.

`user_sessions`:

- `id uuid primary key default gen_random_uuid()`
- `user_id uuid not null references users(id) on delete cascade`
- `org_id uuid not null references organizations(id) on delete cascade`
- `token_hash bytea not null unique`
- `created_at timestamptz not null default now()`
- `last_seen_at timestamptz`
- `expires_at timestamptz not null`
- `revoked_at timestamptz`
- Foreign key `(org_id, user_id)` references memberships for org membership integrity if Postgres accepts it with the existing unique constraint.
- Index: `user_sessions_user_active_idx` on `(user_id, expires_at desc)` where `revoked_at is null`.
- Index: `user_sessions_expiry_idx` on `expires_at` for cleanup.

Public signup must not use the existing bootstrap `create_organization` semantics because that helper intentionally reuses slugs for bootstrap/idempotent setup. A separate onboarding store function must be insert-only and return `409` on slug conflict, so a new user cannot become owner of an existing org by picking the same slug.

Session lookup must join the current membership and require `memberships.status='active'`. Invited, removed, expired, revoked, cross-org, member/viewer-admin, and owner/admin cases need explicit tests. A teammate reserved as `invited` becomes `active` only when they authenticate with a verified provider identity matching the invited email; until that transition, they cannot use the session for dashboard or admin access.

Sessions expire after 30 days by default. The worker should delete expired or revoked sessions after a short retention window alongside existing idempotency cleanup.

### Route Auth Matrix

- Public marketing/auth discovery: no auth.
- Auth session create/logout/current session: cookie/session-aware, no API-key fallback except for test/bootstrap where explicitly documented.
- Dashboard reads: session membership for hosted org data; local unauthenticated fallback remains only for compatibility local product routes.
- UI mutations such as run tags/notes: session membership may authorize when the user has `owner`, `admin`, or `member` role; API-key compatibility continues to require existing scopes.
- SDK ingestion and artifact writes: API key with existing scopes; browser session does not become the SDK hot path.
- Imports, usage, and API-key admin: owner/admin session, configured bootstrap token, or unrestricted org API key with the required scope.
- Org seat/admin routes: owner/admin session or configured bootstrap token only; no unauthenticated local-mode fallback.

## API Contracts

`GET /api/auth/config`

Response:

```json
{ "dev_auth_enabled": true, "managed_google_enabled": false }
```

`POST /api/auth/dev/google`

Request:

```json
{
  "email": "ada@example.com",
  "display_name": "Ada",
  "account_type": "business",
  "org_name": "Ada Lab",
  "seat_emails": ["teammate@example.com"]
}
```

Response:

```json
{
  "authenticated": true,
  "user": { "id": "...", "primary_email": "ada@example.com", "display_name": "Ada" },
  "organization": { "id": "...", "slug": "ada-lab", "name": "Ada Lab", "account_type": "business", "seat_limit": 3 },
  "membership": { "role": "owner", "status": "active" }
}
```

`POST /api/auth/google`

- Same response when configured.
- Returns a client-safe auth/configuration error until real Google verification is configured.

`GET /api/auth/session`

- Returns `{ "authenticated": false }` when no valid session exists.
- Returns current user, organization, membership, and memberships for valid sessions.

`POST /api/auth/logout`

- Returns `{ "authenticated": false }` and clears the cookie.

`POST /api/orgs/:org_id/seats`

Request:

```json
{ "email": "teammate@example.com", "role": "member" }
```

Response:

```json
{ "membership": { "org_id": "...", "user_id": "...", "role": "member", "status": "invited" } }
```

Errors:

- `400`: invalid email, role, account type, org name, or body.
- `401`: missing session/API key/bootstrap where required.
- `403`: user is not an owner/admin of the org.
- `409`: seat limit exceeded.
- `501`: managed Google verification not configured.

Onboarding-created API keys should default to the smallest useful training-loop scopes: `sdk:ingest`, `artifacts:write`, and `export:read`. `imports:write` remains opt-in rather than a default onboarding scope.

Session handlers must override `created_by_user_id` from the authenticated session user and must not trust client-supplied actor fields. Audit events should record actor identity when the helper supports it; until then metadata must include the authenticated actor user ID.

## Performance Considerations

- Session lookup is one indexed equality query on `token_hash` plus membership/org/user join.
- Session `last_seen_at` writes are rate-limited to once per minute.
- Onboarding writes are low frequency and transactional.
- Seat list and usage counts stay small relative to runs/metrics; `memberships(org_id, status, created_at desc)` supports admin views.
- Dashboard list/metric performance remains governed by existing bounded summary and metric-series endpoints; no auth endpoint should fetch metric history.
- API-key plaintext generation reuses the current random 32-byte key path and stores only SHA-256 hashes.
- Manual benchmark target: auth session resolution plus dashboard first useful render should stay under 1 second locally for the 1,000-run demo.
- Request budgets: unauthenticated `/` performs no dashboard data requests; `/signin` performs only auth config/session checks; authenticated `/dashboard/runs` performs at most one session check plus the existing overview/projects/run-summary requests on first load. Tab changes should not refetch dashboard summary unless route state or filters changed.

## Simplicity Review

This design avoids adding a full auth provider SDK, password storage, email delivery, billing, invitation acceptance, or new SDK auth concepts. The browser auth slice is only enough to create user/org/session context and exercise the existing org/API-key data model.

The main complexity intentionally accepted is session-cookie storage, because dashboard auth should not rely on local storage bearer tokens.

## Failure Modes

- Missing Google configuration: production Google route returns a clear client-safe error and the UI can keep the local dev flow available in development.
- Session expired or revoked: session endpoint returns unauthenticated and dashboard redirects to sign-in.
- Seat limit exceeded: seat route returns `409`; onboarding keeps existing seats visible and does not create partial extra seats.
- API key creation fails: onboarding remains incomplete and does not claim the plaintext key exists.
- Old hash URLs: client normalization routes users to the matching path tab.
- Cross-org access: session authorization checks membership against the requested org before API-key or seat mutations.

## Alternatives Considered

- Clerk-only implementation now: better production auth, but impossible to fully test locally without provider credentials and would couple the first slice to a vendor before the app’s own membership/API-key model is exercised.
- Local-storage browser bearer token: simpler, but weaker against XSS and not appropriate for the hosted path.
- Reusing API keys for human browser sessions: avoids a table, but conflates human sessions with SDK service-account keys and makes revocation/audit semantics muddy.
- Full email invitations: useful later, but not needed for the first durable seat mapping.

## Review Notes

Fresh UI reviewer:

- Finding: The direction matches the current dashboard style, but Google auth must not appear broken when managed credentials are absent; route-backed navigation needs link/focus semantics; seat reservation can imply email invitations that do not exist; and responsive/accessibility acceptance criteria were under-specified.
- Risk: A public first impression could feel unfinished, inaccessible, or misleading even if the backend works.
- Recommended edit: Add provider availability discovery, hide/disable unavailable Google auth, use link-equivalent route navigation with `aria-current`, label reserved seats clearly, and define concrete responsive/accessibility acceptance criteria.
- Decision: Revised in this design; UI slice is acceptable after those constraints are implemented.

Fresh backend reviewer 1:

- Finding: The existing identity/org/API-key tables are the right backbone, but public signup must not reuse bootstrap DTOs/helpers that trust `owner_user_id`, `created_by_user_id`, or `plan_tier`. Cookie auth also needs non-permissive state-changing request checks.
- Risk: Slug collision could grant ownership of an existing org; browser requests could forge privileged state changes; default onboarding keys could be over-scoped.
- Recommended edit: Add narrow onboarding/session store functions, make org creation insert-only with `409` on slug conflict, require verified identity, authorize by user UUID and role, add session cookies with hashed opaque tokens, check origin for cookie-auth mutation, and use smaller default onboarding scopes.
- Decision: Revised in this design; backend slice is acceptable if implementation follows these constraints.

Fresh backend reviewer 2:

- Finding: Org create-or-reuse can become tenant takeover; local-mode bootstrap semantics can leave admin routes open; dev auth can become a hosted bypass; seat limit needs transaction locking; session lookup must require active membership; route classes and session cleanup need explicit rules.
- Risk: Tenant takeover, unauthorized API-key creation, forged sessions in hosted mode, seat over-allocation under concurrency, stale/low-role memberships retaining access, and unclear browser/API-key authorization behavior.
- Recommended edit: Use insert-only org creation with `409` conflicts, separate local product fallback from admin authorization, limit dev auth to local mode, lock org rows for seat reservation, require active memberships for sessions, reject unverified identity links, override actor fields from session context, add route auth matrix, and clean expired sessions in the worker.
- Decision: Revised in this design; accepted for implementation with these constraints.

## Coverage Exceptions

None planned.

## Decision

Accepted for a narrow first slice: local/dev Google-style onboarding, opaque browser sessions, route-backed landing/auth/onboarding/dashboard flow, race-safe seat reservation, owner/admin API-key creation, provider availability discovery, and tests/docs. Full production Google verification, email invitation delivery, billing, and broader role-based dashboard permissions remain deferred.
