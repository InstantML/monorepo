# Design: MCP OAuth Authentication

Date: 2026-06-30

Status: Enabled in production (2026-07-02) — auth review passed and the org-scoped bridge is live-verified end to end; prod deploys set `INSTANTML_MCP_OAUTH_ENABLED=1` via `deploy-cloud-run.yml`, staging stays off

Owner: Casablanca

## Summary

The hosted MCP server at `https://mcp.instantml.ai/mcp` authenticates with an
InstantML API key passed as a bearer token. The
`2026-06-30-zero-friction-mcp-setup.md` design named browser-based MCP OAuth as
the true zero-friction endpoint and deferred it pending a fresh auth review.

This design covers adding OAuth so a user can connect an agent by URL alone and
complete a browser sign-in instead of copying a key. It splits the work into a
**safe discovery slice that is implemented now** and a **token-acceptance bridge
that stays gated on the auth review**.

What ships in this slice (opt-in, non-breaking):

- The MCP server advertises RFC 9728 protected-resource metadata at
  `/.well-known/oauth-protected-resource`.
- Unauthenticated `/mcp` requests receive a `401` with a `WWW-Authenticate:
  Bearer resource_metadata="…"` challenge so OAuth-capable clients (Claude Code,
  Cursor, VS Code) start discovery.
- The dashboard **Connect Agent** panel offers an **API key** vs **Browser
  sign-in** choice and generates the tokenless connect snippet for OAuth.

What stays deferred (separate auth review):

- The authorization server itself (consent, PKCE, dynamic client registration,
  token issuance, revocation). We delegate this to Clerk rather than minting
  tokens in the MCP process.
- The MCP-server → Rust-API token bridge that maps a verified OAuth identity to
  an org-scoped, scope-checked request.

## Goals

- Let an agent connect to the hosted MCP server without a copied secret, using a
  standards-compliant browser OAuth flow.
- Keep the API-key bearer path working unchanged as the default and as a
  fallback for clients without OAuth support.
- Reuse InstantML's existing identity provider (Clerk) for consent, client
  registration, and token issuance instead of building a new auth stack.
- Preserve existing org/project scope enforcement — OAuth must not become a path
  that bypasses the API-key scope checks the Rust API already applies.

## Non-Goals

- Do not mint or store access tokens inside the MCP server process.
- Do not change the MCP tool contract or the bounded read limits.
- Do not loosen Rust data-plane authorization to accept unverified identities.
- Do not enable OAuth in production until the authorization server is configured
  and the token bridge passes auth review.

## Users and Use Cases

Primary users are workspace members who want an agent to inspect and compare
runs. The OAuth happy path:

1. In the dashboard **API** tab, choose **Browser sign-in** and copy the
   tokenless snippet for the client.
2. Add the server; on first connect the client opens a browser to InstantML.
3. The signed-in user approves the requested scopes for their org.
4. The client receives a short-lived token and the agent lists recent runs.

Browser sign-in also helps non-admins, who cannot create API keys today but can
authorize an agent as themselves.

## Proposed Design

### Implemented: discovery + challenge (MCP server)

`tools/mcp-server.mjs` gains an opt-in OAuth layer, enabled only when
`INSTANTML_MCP_OAUTH_AUTH_SERVER` is set:

- `parseOAuthConfig(env)` returns `null` by default. When the auth-server issuer
  URL is configured it derives the resource identifier
  (`https://mcp.instantml.ai/mcp`), the metadata URL, and supported scopes
  (`export:read reports:write` by default, overridable).
- `GET /.well-known/oauth-protected-resource` returns RFC 9728 metadata:
  `resource`, `authorization_servers`, `scopes_supported`,
  `bearer_methods_supported: ["header"]`, and a docs link.
- A `/mcp` request with no bearer token returns `401` plus
  `WWW-Authenticate: Bearer resource_metadata="…", error="invalid_token"`.
  `WWW-Authenticate` is added to `Access-Control-Expose-Headers` for browser
  clients.

When OAuth is off (the default and current production state) behavior is
byte-identical to before: no well-known route, and the unauthenticated `/mcp`
response is the existing `Missing Authorization bearer token` JSON-RPC error.
This is covered by `tools/tests/mcp-oauth.test.js` and the unchanged
`tools/tests/mcp-server-entrypoint.test.js`.

### Implemented: dashboard surface

The **Connect Agent** panel (`apps/web/app/dashboard/api/`) adds an auth-method
toggle. **Browser sign-in** generates URL-only client snippets (no
`Authorization` header), which is what triggers the client OAuth flow. The
option carries a **Preview** tag until the end-to-end flow is enabled in
production.

### Authorization server (Clerk) — enabled

Clerk owns the OAuth authorization server: dynamic client registration, the
consent screen, PKCE, and access-token issuance. The MCP server only advertises
Clerk as the `authorization_servers` entry; it never issues tokens. **Dynamic
client registration is enabled** in the Clerk dashboard (instance-level toggle),
so MCP clients self-register during the flow — no per-client OAuth app is
created. Note Clerk does not yet support custom OAuth scopes, so the access token
carries coarse identity scopes only; fine-grained authorization is enforced
server-side by the token-acceptance bridge below, not by token scopes.

### Token-acceptance bridge (MCP server → Rust API) — planned

Clerk DCR and discovery are live, so a client can sign in and obtain an OAuth
access token today; the remaining work is to make the InstantML API accept that
token. The identity → org → role plumbing already exists: the web dashboard maps
a Clerk user to an internal user via the `identities` table
(`provider = "clerk"`, `provider_subject = <clerk user id>`) and resolves
`memberships` to an org and role. The bridge reuses it and keeps the Rust API as
the single auth authority.

Flow — a third bearer tier in `src/http/handlers/helpers.rs` `context()` (today
only API key and session cookie):

1. The MCP server forwards the caller's `Authorization: Bearer <clerk oauth
   token>` to the Rust API unchanged (`tools/mcp-server-tools.mjs`).
2. `context()` sees a bearer that is not an `instantml_` API key and, when the
   bridge flag is on, verifies it as a Clerk OAuth access token.
3. Map the Clerk user (`sub`) to the internal user via `identities`.
4. Resolve the user's active memberships, pick the org (below), and build a
   read-only `RequestContext` so every existing handler scope check applies
   unchanged.

#### Decisions (agreed)

- **Org selection.** An OAuth token carries no InstantML org (InstantML orgs are
  not Clerk orgs). One MCP connection is scoped to one InstantML workspace. The
  dashboard generates OAuth snippets with `?org_id=<uuid>` for the current
  workspace; the MCP server forwards that value to Rust as
  `X-InstantML-OAuth-Org-Id`; Rust verifies the OAuth user is an active member of
  that org before loading tenant data. If no org is named, single-membership
  users still resolve to their only org; multi-org users are rejected with a
  clear error. This prevents silently acting in the wrong tenant while keeping
  the first-time/single-workspace path simple.
- **Permission level (v1): read-only.** The scaffold reuses the existing session
  read-only enforcement — `require_session_scope` allows only `export:read` when
  `demo_read_only` is set — so v1 needs no new scope path. A dedicated read-only
  flag with its own message is the clean follow-up.
- **Permission level (follow-up, reviewed): mirror role.** Grant the user's role
  in that org (viewer → read, admin → report writes), never exceeding the user's
  own access.
- **Parity.** Membership is re-checked on every request, so removing a user or
  changing their role takes effect immediately; revocation, demo read-only, rate
  limits, and audit inherit the existing paths.

#### Endpoint and schema (confirmed)

Resolved from Clerk's official SDK (`clerk/clerk-sdk-python`, Backend API base
`https://api.clerk.com/v1`): the verifier posts to
`/v1/oauth_applications/access_tokens/verify` with the Clerk secret key. The
active-token response is `object=clerk_idp_oauth_access_token` with `subject`
(the Clerk user id), `scopes`, `revoked`, and `expired`; an inactive token
returns `{ "active": false }`. The verifier accepts `subject`/`scopes` and
rejects revoked, expired, and inactive tokens. Verifications are cached by token
hash (bounded to the token's own expiry, capped at 60s) so the Backend API call
stays off the per-request hot path. Clerk's type comments describe these as JWT
access tokens, so a further optimization could verify locally via the existing
JWKS path (`verify_clerk_session_token`) and drop the Backend API call entirely.

#### Implementation (flag-off)

The bridge is implemented behind `INSTANTML_MCP_OAUTH_ENABLED` (default off), so
with the flag unset — the production state — `context()` is byte-identical to
today. The pieces:

- `src/managed_auth.rs` `verify_clerk_oauth_token`: posts the token to the Clerk
  Backend API (`/v1/oauth_applications/access_tokens/verify`) authenticated with
  the existing Clerk secret key, returns the verified subject + scopes, and
  rejects revoked/expired/inactive tokens (endpoint and response shape confirmed
  against Clerk's SDK).
- `src/store/auth/sessions.rs` `authenticate_oauth_identity` /
  `resolve_oauth_identity`: maps the Clerk subject to the internal user via the
  `identities` projection and resolves the named active membership's org/role
  when `X-InstantML-OAuth-Org-Id` is present. Without a named org, it keeps the
  single active membership fallback and rejects unknown identities,
  no-membership, and multi-org.
- `src/http/handlers/helpers.rs` `context()`: the third bearer tier wires the two
  together and builds a read-only `SessionContext`.
- `tools/mcp-server.mjs` / `tools/mcp-server-tools.mjs`: parse `org_id` from
  the `/mcp` URL and forward it only as the internal InstantML API header; the
  token itself is still verified by Rust and does not self-authorize an org.

Unit tests cover the verify-response parsing, the verification cache
(expiry/purge), and the resolver's accept/reject paths (single-org accept;
unknown / no-membership / multi-org reject — the cross-tenant safety property).
The full browser flow — discovery, dynamic client registration, sign-in, token
issuance, MCP connection — and the Clerk verify call were also confirmed live
against a real token. What remains before production enablement: the fresh auth
review (a wrong org or scope mapping could grant broader access than an
equivalent API key), a normal prod Rust release that carries the bridge (prod
Rust is currently many releases behind), and then setting the flag.

## Component Impact

- MCP server (`tools/mcp-server.mjs`): discovery/challenge + config — live.
- MCP tool bridge (`tools/mcp-server-tools.mjs`): forwards the selected dashboard
  org to Rust with `X-InstantML-OAuth-Org-Id` for OAuth snippets that include
  `?org_id=<uuid>`.
- Frontend (`apps/web/app/dashboard/api/`): auth-method toggle and tokenless
  snippets — live; browser sign-in snippets are scoped to the current dashboard
  workspace.
- Rust server: token-acceptance bridge implemented flag-off — verifier + cache
  (`src/managed_auth.rs`), identity→org→role resolution (`src/store/auth/sessions.rs`),
  and the read-only third bearer tier (`src/http/handlers/helpers.rs`). Enabling
  in prod needs the auth review and a normal prod Rust release carrying the bridge.
- Identity provider (Clerk): DCR enabled; the authorization server is configured.
- Docs: `apps/docs/sdk/agent-mcp.mdx` documents browser sign-in as a preview.

## Data Model

- This slice adds no entities.
- The deferred bridge prefers locally verifiable signed tokens over new
  token-storage tables. Any grant/consent or revocation records remain part of
  Clerk's authorization-server responsibility.

## API Contracts

- New unauthenticated route on the MCP server:
  `GET /.well-known/oauth-protected-resource` (and the `/mcp`-suffixed variant).
- New `401` response header on `/mcp`: `WWW-Authenticate` with
  `resource_metadata`.
- OAuth MCP URLs may include `org_id=<uuid>`. This does not change the JSON-RPC
  tool contract; the MCP bridge turns it into the internal
  `X-InstantML-OAuth-Org-Id` API header. Rust honors that header only after the
  bearer token verifies as Clerk OAuth and the subject is an active member of
  the named org.

## Performance Considerations

- Metadata and challenge responses are static and off the tool hot path.
- The deferred bridge must keep token verification bounded — verify signed
  tokens locally and cache JWKS, avoiding a per-tool-call provider round trip.

## Security and Simplicity Review

- Discovery and challenge grant nothing; they only tell a client where to
  authenticate. They are safe to ship independently of the token bridge.
- OAuth is opt-in via env, so production stays on the reviewed API-key path
  until the bridge and Clerk config land.
- Delegating the authorization server to Clerk avoids inventing token storage,
  consent, and revocation.
- The flagged risk (token grants bypassing org/project scope checks) is confined
  to the deferred bridge and is the explicit subject of the auth review.

## Failure Modes

- Client without OAuth support: it ignores the challenge and uses an API key.
- OAuth enabled but auth server misconfigured: clients fail discovery and can
  fall back to an API key; the API-key path is unaffected.
- Token presented before the bridge ships: the Rust API rejects it as today, so
  no unauthorized access is possible.

## Testing Plan

- `tools/tests/mcp-oauth.test.js`: `parseOAuthConfig` defaults/overrides,
  metadata shape, the served metadata route, the `WWW-Authenticate` challenge,
  and that the default (no-OAuth) mode advertises nothing and keeps the original
  401 message.
- `tools/tests/mcp-server-entrypoint.test.js`: unchanged, proving the default
  path is non-breaking.
- Frontend source tests assert the Connect Agent panel exposes browser sign-in
  and that snippets support a tokenless OAuth mode.
- The bridge implementation must add **cross-tenant isolation tests**: a token
  for a user in org A cannot read or write org B; a multi-org user is rejected
  until they name an org; a named org resolves only when the user has an active
  membership; and a read-only (v1) token is denied every write scope.
- End-to-end OAuth tests (sign-in → token → tool call) land with the verifier.

## Decision

Discovery/challenge and the dashboard surface are shipped; Clerk DCR is enabled.
The token-acceptance bridge is scaffolded flag-off (`INSTANTML_MCP_OAUTH_ENABLED`)
so its surface is reviewable, but stays disabled in production until the verifier,
org-resolution, and read-only enforcement complete a fresh auth review. Agreed v1
shape: `?org_id=<uuid>` from the MCP URL → verify active membership in that org;
no org + single active membership → that org; no org + multiple memberships →
reject; read-only permissions, with mirror-role as a reviewed follow-up.

## Enablement (2026-07-02)

The auth review passed and the flag is on in production; `deploy-cloud-run.yml`
sets it per environment (prod `1`, staging unset) so redeploys keep it enabled.
What the review and the live prod test confirmed:

- Org scoping end to end: a fresh mcp-remote DCR sign-in through the org-scoped
  URL listed real runs; a second member org resolved to its own (empty) data;
  no-org multi-org and non-member-org requests were rejected with the intended
  403s; a non-UUID `org_id` fails MCP-side validation.
- Write denial at two layers: the MCP bridge sends no `Origin`, so
  session-context mutations fail the origin gate; a direct API call with a
  spoofed allowlisted `Origin` is still denied by the `demo_read_only` scope
  gate. Reads require `export:read`, which the bridge grants.
- Verifier hygiene: tokens are never logged; verification results are cached by
  token hash for at most 60s (bounded by token expiry); revoked/expired/inactive
  tokens are rejected.

Reviewed follow-ups, in priority order:

1. Negative-cache failed verifications: every garbage bearer currently costs
   one Clerk Backend API round trip while the flag is on (API keys unaffected).
2. Dedicated read-only flag + error message: OAuth write attempts currently
   return the misleading `demo workspace browser sessions are read-only` copy.
3. Mirror-role permissions (previously agreed follow-up).
