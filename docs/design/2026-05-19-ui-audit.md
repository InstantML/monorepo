# UI audit — landing page + dashboard (2026-05-19)

Author: comprehensive UI review for demo-readiness against the calibrated
positioning in [wiki/concepts/honest-moat-assessment.md](../../../product/wiki/concepts/honest-moat-assessment.md).

## Summary

The landing page and dashboard are in good shape structurally and visually
— typography is consistent, dark/light parity is wired, the runs workspace
delivers the core workflow (selection, panels, compare, run detail), and the
codebase has no obvious dead components or broken imports. The pieces that
keep the UI from being demo-ready against the *calibrated* positioning are
narrower and more specific:

1. **Factual technology mis-statement on the landing page** — three places
   call the storage engine "Postgres" when the production server is Rust +
   ClickHouse. Cannot ship this in front of Arjun-class buyers.
2. **Direct contradiction between landing matrix and dashboard config** on
   W&B / MLflow importer status (landing says shipped, dashboard says
   planned). Both ship today as JSON · CLI per `tools/import-*.mjs`.
3. **Zero surface for MCP / agent substrate** in either the landing or
   dashboard. The wiki names MCP-as-protocol as the single novel
   differentiator, and the UI doesn't reference it.
4. **Landing pitch is "speed + price" only** — exactly the [Aim](../../../product/wiki/competitors/aim.md)
   wedge that the category graveyard says fails in isolation. No MCP, no
   integrations distribution narrative, no agent/researcher framing.

None of those are catastrophic; none require redesign. The audit ships
trivial code fixes for the technology mis-statement and the importer status
inconsistency; everything else is recommendations.

## Audience-fit by buyer

### Jay-class team buyer (cost + seat-sharing pain)

- Signup flow exposes Free / Pro / Premium with seat counts and storage
  caps explicitly — ✓ this hits Jay's pain point directly.
- "Reserved seats" textarea for Business tier so Jay can list teammates
  at signup — ✓.
- Seat invite flow exists in Settings → Seats. Member / Admin / Viewer
  roles. ✓
- **Missing for Jay's demo flow**: shareable read-only **project link**
  so Jay can hand a "look at this run" URL to a teammate without burning
  a seat. The wiki's [unlimited-viewer-seats](../../../product/wiki/decisions/unlimited-viewer-seats.md)
  decision is the load-bearing differentiation against W&B's per-seat
  pricing — and there's no share dialog / public-link UI to demonstrate
  that promise. The pitch says "unlimited free read seats" but the UX
  to invoke that requires creating a viewer seat per recipient.

**Verdict**: solid signup-side coverage. The "unlimited viewer seats" demo
hook is structurally promised in the pricing copy but not exercisable in
the UI yet.

### Arjun-class scale user (90k runs, MCP-curious, agent-wrapping-W&B-by-hand)

- Run list and chart workflow hits his bar on speed (145 ms p95 hosted
  per the wiki).
- Compare view supports row / column layouts, diff-only, tags / notes,
  artifact playback. ✓
- Run detail has tags, notes, KPI cards, metric summary, timeline,
  reproducibility (algo / seed / LR / batch). ✓
- **Missing**: any indication that an MCP server / agent surface exists.
  The API tab lists 8 REST routes; there is no `tracker.list_runs`,
  `tracker.query_metrics`, `tracker.get_run` tool listing, no copyable
  Claude Code / Cursor config snippet, no "Use with agents" section.
  Per the [eshaan-demo-runbook](../../../product/wiki/plans/eshaan-demo-runbook.md)
  the MCP server is the **hero moment** of the demo. The UI does not
  reflect that this is a product surface we ship.
- **Missing**: chart density 2D target (per-series × N-series) is not
  surfaced as a benchmark anywhere — Arjun's specific workload (200k
  pts/series × ~2000 plots) is the calibration point the wiki says
  matters most, and the landing headlines "150k points" / "90k runs"
  numbers without naming the chart-density story.

**Verdict**: workflow surface is competent. The novel differentiation
(MCP-as-protocol) is invisible to Arjun browsing the UI.

### Eshaan-class researcher (design partner, visual debugging, intelligence layer)

- Image / audio / video artifacts render inline via `ArtifactMediaPreview`. ✓
- Rich-object panel exists for tables, histograms, rollouts. ✓
- **Deliberately scoped out for v1**: L-pic per-checkpoint image grid,
  side-by-side image diffing. Per [honest-moat-assessment](../../../product/wiki/concepts/honest-moat-assessment.md)
  Eshaan is a design partner not a v1 conversion target. The demo
  runbook treats the L-pic view as a "follow-up offer at close." So the
  absence of L-pic UI is correct scoping, not a defect.
- **Missing**: any "intelligence layer" or "agent surface" entry point.
  Eshaan's pitch is *"intelligence layer around W&B, not a W&B
  replacement"* — and the current UI has zero affordance that gestures
  toward that v2 direction. For a design-partner conversation that's
  fine; for an ongoing daily-driver pitch later it's a gap.

**Verdict**: Eshaan is not a v1 conversion target, so the UI is appropriate
for the design-partner ask. Treat the demo as the runbook prescribes.

## Specific demo readiness

### Can I do the Eshaan demo from this dashboard?

**Partial** — the substrate side works, the MCP side requires the
out-of-monorepo `tools/mcp-server.mjs` and a Claude Code window pointed
at it. The runbook itself is explicit that the MCP server is "demo-prep,
not product" and that you run it via stdio from Claude Code, not from the
dashboard. So:

- Act 1 (solo InstantML substrate, 100k-run table + chart): ✓ supported by the dashboard
- Act 2 (side-by-side speed): ✓ runs-list page is the surface
- Act 3 (cross-run aggregation): partial — the runs table doesn't natively expose `group by LR bucket`; you'd run that query through Claude calling `tracker.list_runs` via MCP
- Act 4 (wrapper friction, the hero): ✗ from the dashboard; ✓ from the Claude Code split-screen exactly as the runbook prescribes
- Act 5 (multi-source via W&B import): ✓ the JSON importer ships
- Act 6 (framing + asks): ✓

The dashboard does not need to host the MCP demo. But if the demo
audience asks "where in the UI do I configure this for my team?" the
answer right now is "you don't yet" — that's a P2 strategic gap and a
real one for any conversation that goes past Eshaan-as-design-partner.

### Can I do the Jay demo?

**Partial.**

What works: Signup flow names plans + seat counts; Settings → Seats lets
you invite by email; the "Reserved seats" textarea at signup is the
direct UX answer to Jay's "we share two seats" pain.

What's missing: the load-bearing piece of the Jay pitch is "free
unlimited viewer seats." Today's UI requires creating a viewer-seat row
for each recipient. The natural Jay demo *should* be: "right-click a
run, copy share link, send to a teammate, teammate opens with no
account." That share-link flow doesn't exist. The pricing claim is in
the product but the UX to invoke it isn't there.

### Can a fresh user sign up and produce a chart in 5 minutes?

Walk-through (code-only):

1. Land on `/` → "Become a design partner" / "Get early access" CTAs both
   point to `/signup`. ✓
2. `/signup` renders `AuthFlow mode="signup"` with the workspace preview
   (Clerk path) or the dev Google form. Plan selection, account type
   (customer / business), org name. ✓
3. Clerk modal verifies identity → server creates workspace +
   onboarding API key in one pass → page swaps to onboarding without
   reload to preserve the copy-once key in memory. ✓ (smart)
4. Onboarding view shows the copy-once key with a terminal-style block
   and "Copy key" button. `export INSTANTML_API_KEY=...` snippet
   visible. ✓
5. "Open dashboard" routes to `/dashboard/runs`. ✓
6. **First-run instructions**: not in-app. The user has to leave the UI,
   read README or external docs, write Python, hit `python train.py`,
   come back. **Missing**: an in-onboarding `pip install instantml` +
   "paste this into a Jupyter cell" code block. The Eshaan-style Python
   snippet on the landing is good — duplicate it inside onboarding so
   the user doesn't context-switch to find it.
7. Empty-workspace state in `/dashboard/runs` shows a helpful callout
   ("This workspace is empty… start by sending your first run with the
   InstantML SDK") with org-switch options if multiple orgs exist. ✓ —
   but doesn't include the actual SDK snippet inline.

**Verdict for 5 minutes**: yes if the user already knows how `wandb.init`
works (or has Claude open). No for a cold first-time user who needs to
discover the SDK call shape inside the product. Add the snippet to the
empty-state callout (P1).

## Recommendations (priority for next 1–2 weeks)

1. **Ship the MCP surface** — even just a docs page + a dashboard
   "Agents" tab with copyable Claude Code config. The runbook treats
   MCP as the hero moment of the demo; the UI should at minimum
   acknowledge the protocol exists. (P2.1)
2. **Replace "PyTorch · JAX · TRL" landing copy** with the v1 must-ship
   frameworks (Lightning, HF Trainer, Ray, Hydra). This is a 1-line copy
   change but a meaningful positioning correction. (P0.3 → recommendation)
3. **Add a project share link / public-viewer flow** so the Jay "unlimited
   viewer seats" promise is exercisable in a demo, not just a pricing
   bullet. (P1.7)
4. **In-product SDK snippet in the empty-workspace state** — the user
   shouldn't have to leave the dashboard to find `pip install instantml`
   and the 3-line `im.init / log / finish` block. (P1.4 + onboarding)
5. **Stop the `#34D399` vs. `#1FB877` brand-color drift** — pick one,
   write a token, kill the hardcoded hexes. (P1.3)
6. **Add `not-found.tsx` + `error.tsx` route handlers** so 404s and
   uncaught errors are branded rather than Next.js default. (P1.1)
7. **Layer the MCP-as-protocol pitch into the landing copy**. Currently
   the pitch is "speed + price" — exactly the Aim wedge that
   [category-graveyard](../../../product/wiki/concepts/category-graveyard.md)
   says fails. The novel differentiation isn't visible. (P2.6)
