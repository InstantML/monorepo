# Imports

InstantML includes local-first import tooling so teams can evaluate without
starting from an empty project or handing third-party credentials to InstantML
servers. The Python CLI reads source data on your machine, normalizes it into
Import v2 chunks, uploads a dry-run summary first, and commits only after you
review the result.

For a screenshot walkthrough of the app flow, see
[W&B and Neptune imports](/guides/wandb-neptune-imports).

## Recommended CLI flow

Use `instantml login` once, then run the source-specific import locally:

```bash
# W&B via the official local wandb SDK.
instantml import wandb --project cartpole --entity my-team --source-project old-project --dry-run

# Real Neptune Exporter Parquet directories.
instantml import neptune --project cartpole --input ./neptune-export --dry-run

# TensorBoard scalar event files (TensorBoard lives under `sync`, not `import`).
instantml sync tensorboard ./runs --project cartpole --dry-run

# Transformed MLflow JSON.
instantml import mlflow --project cartpole --input ./mlflow-export.json --dry-run
```

Remove `--dry-run` only after the summary, warnings, and counts look right.
TensorBoard sync can be repeated; matching imported TensorBoard runs append new
scalar points instead of replacing existing history.

## Supported server routes

| Source shape | Route |
| --- | --- |
| Import v2 jobs | `POST /api/imports/jobs` |
| Import v2 chunks | `POST /api/imports/jobs/{import_id}/chunks` |
| Import v2 commit | `POST /api/imports/jobs/{import_id}/commit` |
| Import v2 cancel | `POST /api/imports/jobs/{import_id}/cancel` |
| W&B transformed JSON | `POST /api/imports/wandb` |
| MLflow transformed JSON | `POST /api/imports/mlflow` |
| Neptune-shaped transformed JSON | `POST /api/imports/neptune` |

These routes accept transformed JSON inputs. They are not raw vendor database
readers. Imports count against the same project, run, metric-point, and
metadata/operational-storage plan limits as SDK writes. Accepted Import v2 chunk
payloads also count as retained operational storage and each import job has a
hard staged-payload byte ceiling, so abandoned dry-run jobs cannot consume
unbounded space. Artifact counts and declared external byte totals are visible
in usage summaries, but importers do not copy source artifact bytes into
InstantML-hosted storage. Storage-heavy migration projects should use Premium
or custom terms before separately uploading retained artifact bytes.

Imported artifact references appear in both places users expect: the legacy raw
run artifact list for backwards-compatible Run Detail and Compare workflows,
and the versioned Artifacts catalog as run-level, metadata-only external
manifest bundles. Those imported catalog versions participate in artifact
lineage, but downloads stay unavailable until you upload the actual bytes with
the SDK.

The legacy JSON routes remain for backward compatibility. New migration work
should prefer Import v2 through the SDK/CLI because it supports dry-run
readiness, warning previews, chunked uploads, real Neptune Exporter Parquet,
direct W&B export, and TensorBoard sync.

## What importers preserve

Importer payloads should preserve the useful experiment-tracking spine:

- Projects.
- Runs.
- Config/params.
- Tags and notes when present.
- Metric history and summaries.
- External artifact references, declared sizes, MIME types, metadata, and
  metadata-only artifact catalog bundles for lineage.
- Import status and diagnostics.

## API-key auth

Importer calls use bearer API keys with import/write permission:

```bash
curl https://api.instantml.ai/api/imports/mlflow \
  -H "Authorization: Bearer instantml_..." \
  -H "Content-Type: application/json" \
  --data @mlflow-transformed.json
```

## Practical migration flow

1. Install the optional integration extra, for example
   `pip install "instantml[imports]"`, `instantml[wandb]`, or
   `instantml[tensorboard]`.
2. Run a dry-run import against one representative project.
3. Review counts, warnings, configs, notes, and artifact references.
4. Open the dashboard and inspect runs, metric counts, configs, notes, and
   artifacts.
5. Repeat for larger projects once the shape looks right.

## Compatibility boundaries

Importers preserve runs, scalar metrics, configs/params, tags, notes, source
provenance, and artifact references. They do not claim full vendor parity for
W&B sweeps/reports/launch, full Neptune namespace semantics, TensorBoard media,
or server-side hosted vendor credential pulls. Source credentials stay local.
